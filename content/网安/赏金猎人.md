## 基本概念

狩猎之前，要了解地形，首先要了解两个经常被视为同义词但实际上**并非如此的**词：

- **信息安全（InfoSec）保护**任何形式的信息：数字信息、纸质信息、对话信息，甚至是锁在抽屉里的合同。这是一个涵盖范围最广的概念；其支柱（如下所示的CIA三要素）既适用于服务器，_也_适用于纸质文档。
- **网络安全**专注于**数字世界**：保护系统、网络、设备和电子数据免受网络威胁。实际上，它是信息安全的一个**分支**（两者有相当大的重叠，但并不相同）。

### 分队

- **防御型（蓝队）：**该团队负责保护、监控、检测、响应和纠正安全漏洞。**蓝队**负责这条防线（安全运营中心、事件响应、_安全加固_）。
- **进攻方（红队）：**指那些在获得授权的情况下，**以攻击为目的**，在攻击者之前发现漏洞的人员。**漏洞赏金计划就属于这一范畴。这**并非单一角色：进攻方涵盖**渗透测试**、**漏洞赏金/漏洞挖掘**以及**红队**本身，红队是一门特定的学科（见下表），并非与“进攻”一词同义。
- **应用安全**涵盖两个方面：**防御**方面（编写安全代码、_威胁建模_、代码审查）和**攻击方面**（测试应用程序漏洞）。漏洞赏金计划在很大程度上属于**攻击性应用安全范畴**。
- **紫队**：红蓝融合。它可以是一个专门负责红蓝作战的团队，也可以是一种**攻防协作的循环工作/演练方法**：攻击者展示攻击_手段_，防御者调整检测和响应策略，双方共同验证修正是否有效。名称源于红蓝组合（红色+蓝色=紫色）。重点并非“另一支队伍发起攻击”，而是**攻防之间的反馈循环**。

# 网络工作原理

网络工作分为三个：客户端，服务端，数据库

- **客户端** ：对于用户使用的，在您的计算机上运行 HTML、CSS 和 JavaScript 。这里的一切都由 您控制，因此**任何仅在客户端进行的安全检查都毫无意义**。隐藏按钮、字段`disabled`、JS 验证：所有这些都可以绕过。
- **服务端**：接收请求，应用**业务逻辑，决定谁可以访问什么资源**，并做出响应。真正的安全机制就存在于此（或者说应该存在于此）。
- **数据库**：用于存储数据（用户、订单、发票等）。服务器查询数据库；客户端**永远不会**直接与数据库交互。==这个就是咱们的最终目标==

欧克，先了解一下最基本的东西，之后看他们是怎么来进行连接的？

    客户端和服务器之间的通信通过**HTTP**（或 HTTPS，即在加密的 TLS 隧道内进行的 HTTP 通信）进行。理解 HTTP 是至关重要的起点：从现在开始，你将使用这种语言进行交流。

## HTTP结构

HTTP 是一种**请求-响应**协议：客户端发送_请求_，服务器发送_响应_。每次交换都是独立的。该协议是**无状态的**（它本身不记住之前的请求；我们稍后会看到 cookie 如何解决这个问题）。

举个例子，先讲一下怎么理解http内容

```http
GET /api/perfil?id=1001 HTTP/2
Host: app.exemplo.com
User-Agent: Mozilla/5.0
Accept: application/json
Cookie: session=abc123
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

分析如下：

- GET /api/perfil?id=1001 HTTP/2 ，表示用的是GET的请求方法，访问了/api/perfil?id=1001这个路径
- 标头：也就是剩下的部分，他表示了这个请求涵盖的一些信息，例如：HOST：主机名，User-Agent：用户的设备（浏览器）信息，cookie：**代表了用户的个人的凭证**（这个也是之后在工作过程中及其重要的一点）
- 正文：剩下的没有体现出来就是，他一般会出现在post或者put传参中

## HTTP方法

| 序号  | 方法      | 描述                                                                             |
| --- | ------- | ------------------------------------------------------------------------------ |
| 1   | GET     | 从服务器获取资源。用于请求数据而不对数据进行更改。例如，从服务器获取网页、图片等。                                      |
| 2   | POST    | 向服务器发送数据以创建新资源。常用于提交表单数据或上传文件。发送的数据包含在请求体中。                                    |
| 3   | PUT     | 向服务器发送数据以更新现有资源。如果资源不存在，则创建新的资源。与 POST 不同，PUT 通常是幂等的，即多次执行相同的 PUT 请求不会产生不同的结果。 |
| 4   | DELETE  | 从服务器删除指定的资源。请求中包含要删除的资源标识符。                                                    |
| 5   | PATCH   | 对资源进行部分修改。与 PUT 类似，但 PATCH 只更改部分数据而不是替换整个资源。                                   |
| 6   | HEAD    | 类似于 GET，但服务器只返回响应的头部，不返回实际数据。用于检查资源的元数据（例如，检查资源是否存在，查看响应的头部信息）。                |
| 7   | OPTIONS | 返回服务器支持的 HTTP 方法。用于检查服务器支持哪些请求方法，通常用于跨域资源共享（CORS）的预检请求。                        |
| 8   | TRACE   | 回显服务器收到的请求，主要用于诊断。客户端可以查看请求在服务器中的处理路径。                                         |
| 9   | CONNECT | 建立一个到服务器的隧道，通常用于 HTTPS 连接。客户端可以通过该隧道发送加密的数据。                                   |

# cookie和session

- **cookie** ：作用于客户端来确定用户的身份
- **session**：作用于服务端来确定用户的身份

## 区别

session和cookie本质上确实是两个东西，但cookie同时也是session id的载体，cookie保存session id。

cookie数据存放在用户的浏览器上，session数据放在网站的服务器上。  
session保存在服务器端与浏览器设置无关，cookie在客户端并受浏览器设置限制。  
cookie是在你的电脑浏览器上保存的,session是在网站服务器上的. 也就是说你换一个电脑你的cookie就不起作用了, 而session只要你的浏览器不关就还能访问到.  
通常的都是两者结合着用的. cookie的话你自己就可以通过对浏览器的设置禁用掉.这样就不起作用了

cookie不是很安全，别人可以分析存放在本地的cookie并进行cookie欺骗，考虑到安全应当使用session。  
session是服务器端缓存，cookie是客户端缓存。  
cookie机制采用的是在客户端保持状态的方案，而session机制采用的是在服务器端保持状态的方案

session会在一定时间内保存在服务器上。当访问增多，会比较占用你服务器的性能，考虑到减轻服务器性能方面，应当使用cookie。  
session是服务器保持客户端状态信息的方案，一般是保存在服务器中的一块内存中，session超时时间在服务器端进行设置。  
cookie是客户端保持用户信息的方案，一般是文件形式保存，cookie清空时间是在客户端浏览器设置。  
从开发角度说，session信息可以通过技术方案写到客户端保存，cookie中的用户信息，也可以在用户访问该网站时，通过技术手段自动更新用户的session信息。

单个cookie保存的数据不能超过4K，很多浏览器都限制一个站点最多保存20个cookie。

建议：将登陆信息等重要信息存放为session；其他信息如果需要保留，可以放在cookie中


举个例子
```http
# 1) # 你登录——服务器创建会话并返回“手环”（令牌）
POST /login HTTP/2
Host: app.exemplo.com
Content-Type: application/json

{"usuario":"alice","senha":"..."}
```

```http
# 服务器返回一个cookie给你
HTTP/2 200 OK
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax   
```

```http
# 2) 在后续的请求中，浏览器会自动重新发送 cookie。
GET /api/perfil HTTP/2
Host: app.exemplo.com
Cookie: session=abc123   
```

你需要识别的三种 Cookie 标志（它们将在后面的多篇文章中出现）：

- **HttpOnly**页面的 JavaScript**无法读取 cookie。这可以缓解通过 XSS 攻击进行的会话劫持。
- **Secure cookie** 只能通过 HTTPS 传输。
- **SameSite**这控制着 cookie 是否会随来自**其他网站的请求一起发送。它是抵御****CSRF**攻击的第一道防线。

# What  a web 漏洞

简单来说就是一个程序他没有按照预期的来进行，导致一些原本不应该被看到的东西被看到，这个就是一个最基本的web漏洞，他基本上都是这个样子的

> [!example] 例子
> 简单来说就是你去开别人的保险库，但是你不知道保险库的密码是多少，但是你试了一个111111的时候，保险库打开了，这个就是一个web漏洞，你不是保险库的拥有者，但是你将里面的东西给试了出来，你看到了保险库里面的东西，这个就是一个错误！

出现web漏洞的错误一般就是服务端那边认可了客户端这边的输入，这个一般会是一个灾难的开始，所有离开浏览器的内容都由用户控制，而将这些信息视为可信信息正是 IDOR、注入攻击、授权绕过以及本系列文章中几乎所有问题的根源。

# 身份验证与授权

这个是一切的基石，需要弄懂这个，后面的很多的东西就会融汇贯通了

另外这两个词有一个天然之间的一个区别，一个是**服务端**认可了你的身份，认为你是一个**合法用户**，另外一个是服务端那边需要确定你这个身份是否可以实行这个权力

> [!example] 例子
> 将服务端比作学校的话，你现在捡了一个学生的学生证，刚好保安没有仔细看，让你过去了，这个就是服务端认可了你的身份。这个时候，你是一个学生，你可以行驶的权利并不是很多，但是如果你是该校的校长的话，那就不一般了。

用代码解释一下

``` js
// 有漏洞的版本 — 验证了你已登录，但没有验证这个请求是你的
function getPedido() {
    if (!usuarioEstaLogado()) {           // 认证：OK
        http_response_code(401);
        return;
    }
    $id = $_GET['id'];                     // <- 信任了客户端传来的 id
    return Pedido::find($id);              // 任何登录用户都能拿到
}

// 正确的版本 — 同时验证所有权（授权）
function getPedido() {
    if (!usuarioEstaLogado()) {
        http_response_code(401);
        return;
    }
    $pedido = Pedido::where('id', $_GET['id'])
                    ->where('dono_id', usuarioLogadoId())  // <- 缺失的检查
                    ->first();
    if (!$pedido) { http_response_code(403); return; }     // 已登录，但不是你的
    return $pedido;
}
```

在上述的代码中，在有问题的那一块会出现一个问题就是**usuarioEstaLogado()** 这个函数只做了这一步，他没有进行下一步的任何的验证操作，直接信任了客户端传输过来的任何的信息，与之相反，的二个给出来的东西，他**usuarioLogadoId()** 这个函数确认了一下客户端发送的id是不是你的，如果不是你的，就会返回403，也就是服务端不认可你的身份。

**作者的忠告：** 你登录不能认为你拥有了一切，身份验证并不等于授权，这个是开发过程中可能会出现的一个问题，但是如果开发懒了一下的话，就是咱们的机会。([[IDOR、BOLA 和 BFLA 的基础到高级应用]])

# OWASP Top 10路线图

OWASP Top 10 是 Web 应用程序中最关键风险类别的列表，由 Open Worldwide Application Security Project（开放式全球应用程序安全项目）维护。它就像是这个领域的地图，值得牢记，因为漏洞赏金计划、分类人员和严重性评级都使用这套语言。

最新版本是 2025 版，但在本文中我们特意按照 [2021 版](https://owasp.org/Top10/2021/)来学习。2021 版至今仍是绝大多数漏洞赏金计划、分类人员和学习材料所使用的参考标准；其中的类别更稳定，也更有助于教学入门。当你掌握了 2021 版后，过渡到 2025 版只需要做一些调整（见表格后面的说明）。以下是 2021 版：

|#|类别|一句话说明|
|---|---|---|
|A01|Broken Access Control（访问控制失效）|访问他人的数据/功能（IDOR、BOLA、BFLA）—— 这是回报最高的类别|
|A02|Cryptographic Failures（加密机制失效）|敏感数据保护不足（缺少 TLS、弱哈希、密钥泄露）|
|A03|Injection（注入）|输入被当作代码/命令执行（SQLi、NoSQLi、命令注入、XSS）|
|A04|Insecure Design（不安全设计）|架构/逻辑缺陷 —— 设计从一开始就是错的|
|A05|Security Misconfiguration（安全配置错误）|配置不当（默认配置、开放面板、缺少响应头）|
|A06|Vulnerable and Outdated Components（易受攻击和过时的组件）|使用带有已知 CVE 的过时库/服务|
|A07|Identification and Authentication Failures（身份识别与认证失败）|登录环节的缺陷（弱密码、会话管理不善、MFA 存在漏洞）|
|A08|Software and Data Integrity Failures（软件与数据完整性失效）|信任未校验完整性的更新/流水线/数据（例如：不安全的反序列化）|
|A09|Security Logging and Monitoring Failures（安全日志记录与监控失效）|没有日志记录/监控 —— 攻击发生了却无人察觉|
|A10|Server-Side Request Forgery（服务器端请求伪造，SSRF）|迫使服务器向你指定的目标发起请求（内网、云元数据）|

不需要一开始就全部背下来。先掌握 A01 和 A03（它们出现频率最高、回报也最高），然后把这份列表当作索引来学习其余部分。

> [!node] 重大消息
>  那么 [OWASP Top 10 2025](https://owasp.org/Top10/2025/) 呢？新版本已经发布并重新调整了列表。值得了解的变化有：Broken Access Control 仍居第 1 位；Security Misconfiguration 上升到第 2 位；Injection 降至第 5 位，Insecure Design 降至第 6 位；Vulnerable and Outdated Components 变成了 Software Supply Chain Failures（第 3 位，范围更广）；SSRF 不再是独立类别，被并入了 Broken Access Control；还新增了一个类别：Mishandling of Exceptional Conditions（第 10 位）。核心思路不变，只是名称和位置有所调整。先学 2021 版（项目仍在使用的版本），然后把 2025 版当作“差异对比”来阅读。

## 赏金计划

> [!node] 什么是赏金计划
>  **漏洞赏金**计划是指公司**授权**外部研究人员查找其系统中的漏洞，并对负责任地报告的有效漏洞**支付奖励**（赏金）。

也就是常说的一些单子，但是，一定不要去接**犯法的单子**，当然你要是快饿死了，那就自己考虑了

当你接赏金计划的时候，有一下前提需要注意
- **只触碰授权范围内的内容。未经授权替换`id`他人系统中的任何内容都属于非法入侵，将受到法律制裁（在巴西，参见《刑法典》第154-A条）。
- **最小概念验证。以尽可能****小**的影响展示缺陷。无需下载整个个人身份信息 (PII) 数据库来“证明”缺陷：一两条经过脱敏处理的记录就足够了。
- **不得造成损害。禁止中断服务、删除生产数据或使用第三方真实账户。
- **负责任地进行举报。首先保护隐私，仅在获得许可的情况下才予以披露。

# 术语表

在接下来的文章中，你会经常遇到这些词。先收藏好：忘了就回到这一节来看。（HTTP、cookie/session、header的术语前面已经解释过了。）

- **API** 是通过代码（而不是界面）与服务器通信的“入口”。通常返回 JSON。它的每个 URL/操作都是一个 **endpoint**（例如：`GET /api/v1/usuarios/1001`）。
    
- **Endpoint**：应用/API 中接受请求的一个具体路径（例如：`/login`、`/api/faturas`）。
    
- **Payload** 是你发送的“内容”。可以是一个请求的正文，或者在攻击中，是你注入的恶意字符串（例如：一个 XSS payload）。
    
- **Token**：登录后用来证明你身份的一种凭据，每次请求时都会发送（通常放在 `Authorization: Bearer ...` 头里）。它取代了每次都要发送密码的做法。
    
- **JWT（JSON Web Token）** 是最常见的 token 类型。它由三部分组成，用点号分隔（header.payload.signature），每部分都是 Base64URL 编码。payload 携带数据（例如：userId、role），signature 保证没有人篡改过 token。⚠️ Base64 不是加密：你可以在 [jwt.io](https://jwt.io/) 上直接读取 JWT 的内容。深入利用见“账户接管（Account Takeover）”一文。
    
- **Hash × 加密 × 编码**（不要混淆，经常考）：
    
    - **编码**（例如：Base64、URL 编码）：只是改变格式，任何人都可以还原。不提供任何保护。
        
    - **Hash**（例如：SHA-256、bcrypt）：单向过程，无法“反哈希”（但如果哈希较弱，可以通过暴力破解来破解）。
        
    - **加密**（例如：AES）：只有拥有密钥才能还原。这才是真正保护机密性的手段。
        
- **TLS / HTTPS**：用于加密浏览器与服务器之间连接的层（也就是那个小锁标志）。证书用来证明网站身份（这也是为什么在第 2b 步中 Burp 要安装它自己的证书）。
    
- **DNS / 子域名 / CNAME**：DNS 把名称（[alvo.com](https://alvo.com/)）翻译成 IP。子域名是 [loja.alvo.com](https://loja.alvo.com/)。CNAME 是一个“别名”，把一个名称指向另一个名称，是“子域名接管（Subdomain Takeover）”一文的核心。
    
- **同源策略（Same-Origin Policy，SOP）** 是浏览器的规则：默认情况下，一个网站不能读取另一个源（域名+端口+协议）的数据。这是浏览器安全的基础。
    
- **CORS** 是以受控方式放宽同源策略的机制（允许特定来源）。如果配置错误，就会变成漏洞。
    
- **CSP（Content Security Policy）**：一个响应头，告诉浏览器脚本/资源可以从哪些地方加载运行。它是防御 XSS 的主要手段。
    
- **WAF（Web Application Firewall）** 是一个“门卫”，在请求到达应用之前过滤可疑请求。它可以被绕过（在本系列中你会看到多种绕过方式）。
    
- **PoC（Proof of Concept）**：证明漏洞存在的最小证据（用于证明的请求/截图），会写进报告里。
    
- **PII**：个人数据（姓名、CPF、邮箱、地址）。泄露 PII = 高影响。
    
- **CVE / CWE / CVSS**：CVE 是公开已知漏洞的“身份证号”（CVE-AAAA-NNNN）；CWE 是漏洞类别；CVSS 是严重性评分。详见“严重性与影响（Severidade e Impacto）”一文。
    
- **Recon / Fuzzing**：recon 是对目标进行测绘（了解存在什么）；fuzzing 是大量发送尝试来发现路径/参数。详见“Recon 与发现（Recon & Discovery）”一文。
    
- **API / GraphQL / Introspection**：除了 REST，很多应用还使用 GraphQL（一个单一的 `/graphql` URL，接受查询）。Introspection 是 GraphQL 的一个功能，可以列出整个 schema（类型、字段、操作）。当它被启用时，对攻击者来说就是金矿。详见“API 安全（Segurança de APIs）”一文。
    
- **Mass Assignment（批量赋值）**：当你在 JSON 请求中发送额外字段（例如：`"role":"admin"`、`"isAdmin":true`），而应用盲目接受并修改了本不该修改的内容。更多内容见“API 安全”一文。
    
- **SSL Pinning**：移动应用只信任某个特定证书，这会卡住 Burp（Burp 的证书会被拒绝）。可以通过 Frida/objection 做 bypass 来解决。见“移动端漏洞赏金（Bug Bounty em Mobile）”。
    
- **Deeplink** 是一种特殊链接（例如：`app://...`），可以打开移动应用的某个特定页面。校验不严的 deeplink 会成为攻击向量。见“移动端（Mobile）”。
    
- **Cloud metadata**：云环境中的一个内部端点（例如：`http://169.254.169.254`），会返回机器的凭据/配置。它是 SSRF 的经典目标 → 见“SSRF”。
    
- **Primitiva / Chaining**：primitiva 是一个漏洞给你的“能力”（读文件、重定向、发起服务端请求……）。Chaining 是把多个小的原语/漏洞串联起来，直到形成严重影响。“漏洞串联（Chaining de Vulnerabilidades）”一文专门讲这个。
    
- **XXE / 外部实体**：在 XML 中，一个“外部实体”（`<!ENTITY x SYSTEM "file:///...">`）会让解析器去获取一个文件/URL。滥用这一点来读取文件或进行 SSRF，就是 XXE。
    
- **序列化 / Gadget chain**：序列化是把一个对象变成字节/字符串（用于保存或传输）；对不可信数据进行反序列化，可能通过串联应用中已有的类（gadget chain）变成 RCE。见“不安全反序列化（Insecure Deserialization）”。
    
- **Prototype Pollution**：通过 `__proto__` 污染 JavaScript 的 `Object.prototype`，从而影响应用中的所有对象。见“原型污染（Prototype Pollution）”。
    
- **S3 / IAM / IMDS**：AWS 云相关术语——S3（bucket 存储）、IAM（身份与权限）、IMDS（metadata 端点 169.254.169.254，可能返回凭据）。见“云与 AWS（Cloud & AWS）”。

## 总结

- 网络由**客户端↔服务器↔数据库组成**，通过**HTTP协议**进行通信。客户端发送的所有内容都是**可控的**，而将其视为完全可信则是大多数故障的根源。
- **身份验证**= “你是谁？”；**授权**= “你能做什么？”。不要混淆它们：这是最赚钱的漏洞的基础。
- OWASP **Top 10 2021**是你的路线图；**A01（访问控制失效）**和**A03（注入攻击）**是入门之选。
- 漏洞赏金是**合法的漏洞挖掘**：阅读范围和规则，使用最小的概念验证，并负责任地披露信息。
- **Burp Suite**就像放大镜：代理拦截、中继器测试、入侵者自动化。
